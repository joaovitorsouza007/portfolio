# Catálogo dos 23 comandos do Impeccable

Este catálogo documenta os 23 comandos do Impeccable, organizados por 
categoria de intervenção. Cada comando é apresentado com nome, 
categoria, finalidade, momento de uso, exemplo de aplicação, riscos e 
evidência de sucesso.

**Projeto de referência:** Portfólio João Vitor Souza — direção 
Proof Ledger (editorial, claro, 1 acento).

---

## Create (Criar)

### 1. `impeccable`

| Campo | Conteúdo |
|-------|----------|
| **Nome** | Impeccable |
| **Categoria** | Criar |
| **Finalidade** | Ponto de entrada do sistema. Descreve o que se quer criar/melhorar e direciona para o comando adequado. |
| **Momento de uso** | No início de qualquer intervenção, quando ainda não se sabe qual comando específico usar. |
| **Exemplo** | "Quero melhorar a seção de projetos do meu portfólio para recrutadores." |
| **Riscos** | Descrição vaga faz o agente escolher o comando errado e gerar retrabalho. |
| **Evidência** | O comando escolhido faz sentido para o problema descrito? |

### 2. `shape`

| Campo | Conteúdo |
|-------|----------|
| **Nome** | Shape |
| **Categoria** | Criar |
| **Finalidade** | Transformar uma ideia solta em um briefing de design construível. |
| **Momento de uso** | Antes de codar, quando se tem só uma intenção ("quero algo moderno"). |
| **Exemplo** | Transformar "quero um portfólio moderno" em "editorial técnico, tipografia forte, 1 acento, muito respiro". |
| **Riscos** | Briefing muito abstrato vira decoração sem função. |
| **Evidência** | O briefing permite decidir tipografia, cor e layout sem ambiguidade. |

## Evaluate (Avaliar)

### 3. `audit`

| Campo | Conteúdo |
|-------|----------|
| **Nome** | Audit |
| **Categoria** | Avaliar |
| **Finalidade** | Encontrar problemas de implementação (contraste, acessibilidade, responsividade) e priorizar correções. |
| **Momento de uso** | Antes de refinar, para saber o que está tecnicamente quebrado. |
| **Exemplo** | "Audite o index.html: contraste WCAG, alt em imagens, foco visível, breakpoints." |
| **Riscos** | Focar só em estética e ignorar acessibilidade real. |
| **Evidência** | Lista de problemas com severidade e correção aplicada. |

### 4. `critique`

| Campo | Conteúdo |
|-------|----------|
| **Nome** | Critique |
| **Categoria** | Avaliar |
| **Finalidade** | Identificar o que está segurando o design (hierarquia, foco, clareza) e o que melhorar primeiro. |
| **Momento de uso** | Depois do audit, para julgar qualidade de design, não só implementação. |
| **Exemplo** | "Critique a home: o que o olho vê primeiro? Está alinhado com o público recrutador?" |
| **Riscos** | Crítica genérica ("está bonito") não gera ação. |
| **Evidência** | 3–5 problemas priorizados com justificativa. |

## Refine (Refinar)

### 5. `animate`

| Campo | Conteúdo |
|-------|----------|
| **Nome** | Animate |
| **Categoria** | Refinar |
| **Finalidade** | Usar movimento para esclarecer mudanças, relações e feedback. |
| **Momento de uso** | Quando transições/estados não estão claros. |
| **Exemplo** | Animação sutil ao abrir um projeto, hover em botão, fade no formulário. |
| **Riscos** | Excesso de animação distrai e prejudica performance. |
| **Evidência** | O movimento comunica algo (não é só enfeite)? |

### 6. `bolder`

| Campo | Conteúdo |
|-------|----------|
| **Nome** | Bolder |
| **Categoria** | Refinar |
| **Finalidade** | Dar mais presença a uma seção mantendo fidelidade ao design. |
| **Momento de uso** | Quando uma seção importante está "apagada". |
| **Exemplo** | Hero com tipografia maior, mais contraste, mais respiro. |
| **Riscos** | Exagerar e quebrar a hierarquia global. |
| **Evidência** | A seção agora é o ponto focal natural? |

### 7. `colorize`

| Campo | Conteúdo |
|-------|----------|
| **Nome** | Colorize |
| **Categoria** | Refinar |
| **Finalidade** | Usar cor para esclarecer ações, estados e caráter do design. |
| **Momento de uso** | Quando tudo tem o mesmo peso cromático. |
| **Exemplo** | 1 acento só para CTA, estados de erro/sucesso. |
| **Riscos** | Muitas cores → volta o "slop de IA". |
| **Evidência** | A cor guia o olho para a ação certa? |

### 8. `delight`

| Campo | Conteúdo |
|-------|----------|
| **Nome** | Delight |
| **Categoria** | Refinar |
| **Finalidade** | Tornar momentos significativos surpreendentes e memoráveis. |
| **Momento de uso** | Pontos de contato importantes (contato, primeiro projeto). |
| **Exemplo** | Microinteração no envio do formulário. |
| **Riscos** | Virar ruído se aplicado em tudo. |
| **Evidência** | O momento é lembrado sem atrapalhar a tarefa? |

### 9. `layout`

| Campo | Conteúdo |
|-------|----------|
| **Nome** | Layout |
| **Categoria** | Refinar |
| **Finalidade** | Organizar a página para que se saiba onde olhar e o que pertence junto. |
| **Momento de uso** | Quando a leitura está confusa ou o grid é inconsistente. |
| **Exemplo** | Grid de 12 colunas, alinhamento à esquerda, agrupamento de projetos. |
| **Riscos** | Layout "bonito" que não reflete a prioridade do conteúdo. |
| **Evidência** | O olho segue uma ordem lógica? |

### 10. `overdrive`

| Campo | Conteúdo |
|-------|----------|
| **Nome** | Overdrive |
| **Categoria** | Refinar |
| **Finalidade** | Ir além do esperado e fazer a interface parecer extraordinária. |
| **Momento de uso** | Quando o design está correto mas sem personalidade. |
| **Exemplo** | Tipografia display ousada no hero, composição editorial. |
| **Riscos** | Exagero quebra usabilidade e credibilidade. |
| **Evidência** | Ainda é usável e memorável? |

### 11. `quieter`

| Campo | Conteúdo |
|-------|----------|
| **Nome** | Quieter |
| **Categoria** | Refinar |
| **Finalidade** | Reduzir ruído visual mantendo a personalidade. |
| **Momento de uso** | Quando há muitos elementos competindo. |
| **Exemplo** | Remover sombras, reduzir bordas, diminuir ícones. |
| **Riscos** | Ficar sem hierarquia nenhuma. |
| **Evidência** | O conteúdo principal respira? |

### 12. `typeset`

| Campo | Conteúdo |
|-------|----------|
| **Nome** | Typeset |
| **Categoria** | Refinar |
| **Finalidade** | Tornar texto fácil de ler, escanear e reconhecer. |
| **Momento de uso** | Quando a tipografia é genérica ou a escala é confusa. |
| **Exemplo** | Display + corpo, escala 12→64, line-height adequado. |
| **Riscos** | Fontes "bonitas" que prejudicam legibilidade. |
| **Evidência** | Dá para escanear a página em 10 segundos? |

## Simplify (Simplificar)

### 13. `adapt`

| Campo | Conteúdo |
|-------|----------|
| **Nome** | Adapt |
| **Categoria** | Simplificar |
| **Finalidade** | Fazer um design existente funcionar em outra tela/dispositivo/plataforma. |
| **Momento de uso** | Ao testar mobile, tablet, ou outro contexto. |
| **Exemplo** | Reorganizar grid de projetos para 1 coluna em mobile. |
| **Riscos** | Só "encolher" sem repensar a hierarquia. |
| **Evidência** | A experiência é boa em 320px, 768px e 1280px? |

### 14. `clarify`

| Campo | Conteúdo |
|-------|----------|
| **Nome** | Clarify |
| **Categoria** | Simplificar |
| **Finalidade** | Ajudar as pessoas a entender o que aconteceu e o que fazer. |
| **Momento de uso** | Textos de estado, erros, instruções. |
| **Exemplo** | Mensagem de erro no formulário, texto de "nenhum projeto ainda". |
| **Riscos** | Texto genérico ("Ops, algo deu errado"). |
| **Evidência** | O usuário sabe o próximo passo? |

### 15. `distill`

| Campo | Conteúdo |
|-------|----------|
| **Nome** | Distill |
| **Categoria** | Simplificar |
| **Finalidade** | Reduzir clutter para o importante ser fácil de encontrar. |
| **Momento de uso** | Quando há excesso de seções, ícones, texto. |
| **Exemplo** | Remover seções redundantes, enxugar copy. |
| **Riscos** | Remover o que dá contexto ao recrutador. |
| **Evidência** | Achar o essencial ficou mais rápido? |

## Harden (Preparar)

### 16. `harden`

| Campo | Conteúdo |
|-------|----------|
| **Nome** | Harden |
| **Categoria** | Preparar |
| **Finalidade** | Manter a interface usável quando dados, conexões ou ações falham. |
| **Momento de uso** | Antes de publicar. |
| **Exemplo** | Estado de erro no formulário, fallback de imagem. |
| **Riscos** | Só tratar o "caminho feliz". |
| **Evidência** | Simular falha e ver se ainda funciona? |

### 17. `onboard`

| Campo | Conteúdo |
|-------|----------|
| **Nome** | Onboard |
| **Categoria** | Preparar |
| **Finalidade** | Ajudar novos usuários a chegar ao primeiro resultado útil. |
| **Momento de uso** | Quando o usuário cai no site sem contexto. |
| **Exemplo** | Hero que diz em 1 frase o que você faz e para quem. |
| **Riscos** | Texto longo que ninguém lê. |
| **Evidência** | Em 5 segundos dá para entender o que o site é? |

### 18. `optimize`

| Campo | Conteúdo |
|-------|----------|
| **Nome** | Optimize |
| **Categoria** | Preparar |
| **Finalidade** | Encontrar o que deixa a interface lenta, corrigir e medir. |
| **Momento de uso** | Quando há imagens grandes, JS desnecessário, fontes pesadas. |
| **Exemplo** | Comprimir imagens, remover Bootstrap local não usado. |
| **Riscos** | Otimizar antes de saber o que é gargalo. |
| **Evidência** | Métricas antes/depois (Lighthouse). |

### 19. `polish`

| Campo | Conteúdo |
|-------|----------|
| **Nome** | Polish |
| **Categoria** | Preparar |
| **Finalidade** | Fazer uma página existente parecer finalizada e funcionar melhor. |
| **Momento de uso** | Última passada antes de publicar. |
| **Exemplo** | Ajustar espaçamento, alinhamento, detalhes de borda. |
| **Riscos** | "Polir" sem ter resolvido estrutura. |
| **Evidência** | Ainda tem algo "quase lá"? |

## System (Sistematizar)

### 20. `document`

| Campo | Conteúdo |
|-------|----------|
| **Nome** | Document |
| **Categoria** | Sistematizar |
| **Finalidade** | Registrar o sistema visual para que trabalhos futuros o sigam. |
| **Momento de uso** | Depois de definir direção visual. |
| **Exemplo** | Criar `DESIGN.md` com tokens, tipografia, cor, componentes. |
| **Riscos** | Documentar antes de decidir → vira burocracia. |
| **Evidência** | Outra pessoa consegue seguir o sistema? |

### 21. `extract`

| Campo | Conteúdo |
|-------|----------|
| **Nome** | Extract |
| **Categoria** | Sistematizar |
| **Finalidade** | Transformar padrões de UI repetidos em componentes e estilos compartilhados. |
| **Momento de uso** | Quando há repetição de card, botão, seção. |
| **Exemplo** | Extrair `.project-card`, `.btn-primary` para reuso. |
| **Riscos** | Abstrair cedo demais e criar complexidade. |
| **Evidência** | Menos duplicação de CSS, mudança em 1 lugar reflete em todos. |

### 22. `generate`

| Campo | Conteúdo |
|-------|----------|
| **Nome** | Generate |
| **Categoria** | Sistematizar |
| **Finalidade** | Nomear um elemento, comparar variações e escolher a melhor. |
| **Momento de uso** | Quando não se sabe qual versão é melhor. |
| **Exemplo** | Gerar 3 versões do hero e comparar. |
| **Riscos** | Escolher por gosto, não por critério. |
| **Evidência** | A escolha é justificável pelo público/objetivo? |

### 23. `live`

| Campo | Conteúdo |
|-------|----------|
| **Nome** | Live |
| **Categoria** | Sistematizar |
| **Finalidade** | Apontar para a página, explorar variações e ficar com a que gosta. |
| **Momento de uso** | Iteração visual rápida. |
| **Exemplo** | Testar 3 variações do hero ao vivo e escolher. |
| **Riscos** | Aceitar a primeira sem comparar. |
| **Evidência** | A versão final é justificadamente a melhor? |
